# RPM 페르소나 시스템 — 기술 설계서

> 프로젝트: RPM (현행 41rpm) · Team 41R
> 목적: **실서비스 전제**의 아키텍처 설계. 본 문서는 기술 분석을 다시 수행하기 위한 기준 문서다.
> 상태: 초안 **v0.4** — 미결 의사결정은 §11에 명시

### v0.4 변경 요약 (2026-06 외부 기술 검증 반영)
이번 개정은 v0.3의 논리 구조를 유지하되, 외부 스택의 실재성·성숙도를 1차 자료로 재확인하고 그 결과를 설계에 정직하게 반영한다.

- **[V1] 설계 타당성 근거를 §0.2로 명문화:** 이 설계가 "왜 논리적으로 타당한가"를 8개 엔지니어링 원칙으로 정리. 각 원칙은 검증된 시스템 설계 원리이며, 본 문서 전체가 이 원칙들의 일관 적용임을 명시.
- **[V2] "trustless" → "trust-minimized" 정직화 (§3·§6·§8):** T2(TEE)조차 모든 신뢰를 제거하지 않는다. **잔여 신뢰 = {AWS Nitro 하드웨어/펌웨어, Seal threshold 키서버 위원회, 매칭 산정 앵커}**. T2가 제거하는 건 *운영자(우리)* 신뢰이지 *전체* 신뢰가 아님을 §6.3·§8에 박음.
- **[V3] Seal의 threshold 위원회 신뢰 명시 (§4.4·§6):** Seal 메인넷은 2025-09-03. 키서버가 다수 제공자(Enoki 등)로 구성된 t-of-n 위원회이므로 "중개자 없음"이 아니라 **"중앙 중개자 → 분산 threshold 위원회"**. 이 위원회 정족수가 잔여 신뢰 가정.
- **[V4] Nautilus 성숙도 강등 (§0.1·§6.1·§9·§11):** Nautilus는 AWS Nitro Enclaves 기반(CPU enclave)이 맞고 대형 LLM 추론 TEE와 무관함은 정확하나, 공식 빌드 템플릿이 **보안 감사 미완료·평가 목적용·기능 미완성**임을 명시. T2는 "TEE 도입 시점 미결"이 아니라 **"TEE 프리미티브 성숙도 자체가 미결"**로 강등.
- **[V5] vLLM 멀티테넌트 프로덕션 서빙 갭 (§9·§11):** 멀티-LoRA 서빙(S-LoRA)은 연구 레벨에서 수천 어댑터 입증됨. 단 vLLM의 *런타임 동적 LoRA 로딩*은 공식적으로 프로덕션 부적합(보안 위험)이고, **모든 레플리카 동기화·재시작 생존을 보장하는 멀티테넌트 프로덕션 서빙은 직접 구축해야 하는 미해결 영역**. Stage 3 로열티 경제성이 여기 의존.
- **[V6] 체인 전환 근거 정밀화 (§0.1):** "Solana엔 대응 프리미티브가 없음"(과장) → **"Sui-native로 수직 통합된 검증저장+threshold게이팅+TEE-attestation 스택이 없음"**. 결론(Sui 전환)은 유지하되 근거 문장을 한 칸 좁힘.
- **[V7] 단위경제 순환 + 진입점 신설 (§7·§11):** 충실도↔지불의사↔인프라원가가 *순환 의존*임을 명시하고, 깨고 들어갈 고리를 **"최소 인프라(T0)에서 충실도 PoC 먼저"**로 §11에 진입점으로 박음.
- **[V8] 재사용 경제를 복리 엔진으로 격상 (§2·§5):** "검증된 페르소나가 N개 캠페인에 재사용"이 진짜 사업적 복리 엔진임을 §2 본문으로 끌어올림(기존엔 §5.1 8단계에 묻혀 있었음).

- **[V9] 마무리 정밀화 (검증 후):** §8 데모그래픽 분산 수치를 "한 자릿수%대(출처 명시 필요)"로 완충, Nautilus를 "프레임워크는 메인넷·*참조 빌드*가 eval-only"로 정밀화(§0.1·§11), 원칙1의 "BFT 동형"→"같은 계열"·"단독 위조 불가(T1+ 기준)"로 시제 정직화(§0.2).
- **[V10] 정합성 2차 패스:** 원칙5의 "trustless"→"운영자 신뢰 제거(T2)"로 자기모순 제거(§0.2), §5.1 5단계를 T0=3중/T1=4-신호로 명시, Nautilus 표현을 "프레임워크 메인넷·프로덕션 빌드 미성숙"으로 전 구간(§3.3·§3.4·§6.1·§9) 통일, §2 Stage 2 입력데이터 칸을 본문(행동·funnel)과 정합.

> 이전 개정 이력(v0.1~v0.3)은 부록 B 참조. v0.3의 핵심 골자(가치명제 정밀화, load-bearing 보정, 상호봉인 민감도 상한, MVP 신뢰 시제 정직화, 멀티-LoRA 어댑터 구조)는 모두 유지된다.

## 0. 문서 범위

- 다루는 것: 설계 타당성 근거, 제품 성숙 로드맵(Stage 1–3), 시스템 아키텍처, 사이드별 책임, 데이터 모델, 캠페인 플로우, 검증 모델, 비용·인센티브, 탈중앙화 타당성, 기술 스택, 구현 스코프, 미결 사항.
- 다루지 않는 것: UI 상세, API 스펙 시그니처, 인프라 IaC. (별도 문서)
- 핵심 설계 명제: **소유는 유저, 표준·과금·검증 앵커는 플랫폼(우리 API), 세션 검증은 기업, 자산·정산은 온체인.**

## 0.1 플랫폼 전제 (확정)

- **체인: Sui (Move) — 전략적으로 확정.** 현행 41rpm 프로토타입은 Solana 위에 있으나, 검증가능 저장(Walrus)이 시스템의 load-bearing 요소이고 Walrus·Seal·Nautilus가 Sui 네이티브 스택이므로 **Sui로 전환**한다. 아직 실서비스 트래픽/자산이 없는 빌드 단계라 마이그레이션 비용은 신규 구현 비용과 사실상 동일 — 듀얼체인 부담 없이 Sui 단일 타깃으로 간다.
- **외부 스택 실재성·성숙도 (2026-06 1차 자료 확인):**
  - **Walrus** — 메인넷 2025-03 출시. RedStuff 2D 소거부호로 4–5배 복제만으로 가용성 확보. **성숙·프로덕션 가용.** 보장 범위 = content-addressing 무결성·가용성(≠ 데이터 진위).
  - **Seal** — 메인넷 2025-09-03 출시. Move 기반 온체인 접근정책 + t-of-n threshold 암호화 + 클라이언트측 암호화. **프로덕션 가용.** ⚠️ 키서버가 다수 제공자(Enoki 등) threshold 위원회 → **잔여 신뢰 가정 있음**(§4.4).
  - **Nautilus(TEE)** — 프레임워크는 메인넷(2025-06-05), AWS Nitro Enclaves 기반(CPU enclave). ⚠️ 단 **공식 *참조 빌드 템플릿*이 보안 감사 미완료·평가 목적용·기능 미완성**(프레임워크 ≠ 프로덕션 준비된 빌드). v2 후보지만 *우리가 실제로 올릴 빌드의 성숙도가 리스크*(§6.1·§11).
- **체인 전환의 1차 근거 (정밀화):** Solana에도 스토리지(Arweave/Irys 등)·접근제어 패턴은 존재한다. RPM이 Sui를 택하는 근거는 "Solana엔 없다"가 아니라, **검증가능-저장(Walrus) + threshold-게이팅(Seal) + TEE-attestation(Nautilus)이 Move-native로 수직 통합된 단일 스택이 Sui에만 있다**는 통합성이다. load-bearing 컴포넌트(Walrus)가 요구하는 것으로 인프라를 고르는 결정이며, 비용이 같은 지금 옮긴다.

## 0.2 설계 원칙 / 타당성 근거 (왜 논리적으로 타당한가)

기술자 관점에서 설계의 타당성은 세 가지로 판정된다 — **(a) 주장한 보장이 실제 메커니즘에서 따라 나오는가, (b) 실패모드가 빠짐없이 커버되거나 명시적으로 수용되는가, (c) 조합했을 때 모순이 없는가.** 본 설계는 아래 8개 검증된 엔지니어링 원칙을 *일관되게* 적용함으로써 세 항목을 통과한다. 이후 모든 §는 이 원칙들의 구체화다.

| # | 원칙 | 어디서 | 무엇을 보장하나 |
|---|---|---|---|
| 1 | **신뢰경계 분리** (separation along trust boundaries) | §3.1 | 3축(소유/실행/표준·검증)이 인센티브가 어긋난 3 principal에 매핑 → 단독 위조 불가 **(T1+ 기준; T0 MVP는 실행 진위에 운영자 신뢰 잔존, §6.3)**. separation of duties / BFT와 *같은 계열*(동형까진 아님) |
| 2 | **단조적 보안 단계** (monotonic staging) | §3.4·§6.3 | T0→T1→T2가 보장을 *추가만* 하고 제거하지 않음. 직교 업그레이드라 big-bang 없이 증분 출시 |
| 3 | **신뢰 컴포넌트 최소화** (minimize trusted components) | §6.4 | 한 장치(플랫폼 샌드박스)가 fake-DOM 갭(§6.2)과 비밀 복사누출(§4.5)을 동시 해소 |
| 4 | **갭→완화책 명시 매핑** (no hand-waving) | §6.2→§6.4 | 무너지는 자리마다 대응책 이름과 의존 순서를 박음("신뢰된 캡처가 TEE의 전제") |
| 5 | **검증 가능한 것만 클레임** (claim only what you verify) | §1.1·§2 | capture-then-react ≠ 자율 브라우징 / 출처 ≠ 충실도 / "운영자 신뢰 제거"는 T2부터(전체 신뢰 제거 아님 — trust-minimized, §6.3). 없는 능력 주장 안 함 |
| 6 | **원자성 불가 시 올바른 대체물** (escrow + 슬래싱) | §4.5.2 | atomic swap이 불가능한 비대칭 교환을 escrow 매개 상태머신 + 본드로 처벌. fair-exchange-with-bond 패턴 |
| 7 | **의존성 기반 인프라 선택** | §0.1 | 인프라를 hype가 아니라 load-bearing 컴포넌트(Walrus) 요구로 선택 |
| 8 | **비용·정산에 맞는 팩토링** | §2·§9 | 동결 base + 페르소나별 LoRA = 표준화(base) + 페르소나 델타(어댑터) + 깨끗한 로열티 단위 |

> **타당성의 경계 (정직):** 위 8개는 설계 *내부* 논리를 자기완결적으로 만든다. 그러나 시스템 전체의 사업적 타당성은 두 개의 *외부 실증 가설* — **코호트별 충실도가 의사결정급 신호인가(§8·§11)**, **단위경제가 성립하는가(§7·§11)** — 위에 선다. 좋은 설계의 특징대로 이 두 가설은 시스템 안에 숨겨지지 않고 §11로 밖에 명시되어 있다. "논리가 틀릴 수 있는 곳"을 설계가 스스로 가리킨다.

## 1. 제품 개요 / 해결 문제

### 1.1 한 줄 정의
진짜 사람의 행동으로 만든, **출처가 검증되고 유저가 소유하는 AI 페르소나**. 기업은 출시 전에 소비자 반응을 시뮬레이션하고, AI 에이전트는 페르소나를 공유 메모리로 쿼리한다.

> **"검증가능"의 정확한 범위 (중요):** 본 시스템이 암호학적으로 증명하는 것은 페르소나 데이터의 **출처·무결성·소유**(이 데이터가 진짜 이 세션에서 나왔고, 변조되지 않았으며, 유저 것이다)이지, **시뮬레이션의 충실도**(페르소나가 실제 인간을 얼마나 잘 예측하는가)가 아니다. 충실도는 별도 — **코호트별 페르소나↔인간 상관 측정**(§8)에서 온다. 즉 *"믿을 수 있는 출처"*는 아키텍처가, *"믿을 수 있는 예측"*은 측정이 보증한다. 이 둘을 한 단어로 뭉치지 않는 것이 본 설계의 정직성 계약이다. (원칙 5)

### 1.2 해결 문제 (3대)
| 문제 | 현상 | RPM의 해소 |
|---|---|---|
| 에이전트 메모리 파편화 | 플랫폼마다 메모리가 고립, 이식·검증 불가 | 이식 가능한 페르소나 메모리 레이어(MemWal) |
| 페르소나 데이터 사일로 | 회사마다 같은 사람을 재분석, 공유 불가 | 유저 소유·온톨로지 구조로 교차 재사용 |
| 합성 유저의 가짜 기반 | 시뮬레이션이 합성/스크래핑 데이터 기반, *출처조차* 불명 | **출처 검증된** 실제 인간 행동 + 기여자 보상 (예측 충실도는 코호트 측정으로 별도 보증) |

### 1.3 핵심 가치
실제 인간 *출처*(provenance) · Walrus 기반 무결성 · 유저 소유(주권) · 기여 보상(인센티브). — *예측 충실도는 §8 코호트 상관에서 오는 별도 축이며, 위 4개와 혼동하지 않는다.*

### 1.4 신뢰의 시제 (단계별로 도착한다)
가치 주장은 **단계별 미래형**이다. MVP(T0)에서 실행 진위는 운영자 신뢰(평판)에 의존 — 이 시점의 제품은 사실상 *"검증 영수증(Walrus/Sui)을 단 중앙 SaaS"*다. **운영자 신뢰 제거는 T2(TEE, §3.4/§6.3)에서 도착**한다(단, 전체 신뢰 제거가 아니라 운영자 신뢰 제거 — §6.3 잔여 신뢰 주). 출처·소유·무결성은 MVP부터 실재하지만, "운영자도 못 속인다"는 T2의 약속이다. §1.1~1.3을 현재형 완성으로 읽지 말 것.

## 2. 제품 성숙 로드맵 (3단계)

페르소나를 **어떻게 표현하느냐**의 사다리. *소유·검증 기층*(유저 소유 + Walrus 무결성)은 단계가 바뀌어도 불변이며 누적된다. 단 **수집하는 데이터의 *종류*는 단계마다 질적으로 깊어진다** — Stage 1은 반응 데이터, Stage 2는 자율 순회의 행동·funnel 데이터, Stage 3은 per-persona LoRA 학습에 충분한 행동 코퍼스. 따라서 Stage 3 충실도는 사실상 성숙한 Stage 2 데이터에 의존한다("더 많은 같은 것"이 아니라 "더 깊은 종류").

> **복리 엔진 = 재사용 경제 (격상):** 진짜 사업적 복리는 추상적 "기층 누적"이 아니라 **검증된 페르소나 1개가 N개 캠페인·에이전트에 재사용**되는 데서 나온다(§5.1 8단계). 한 번 출처 검증된 페르소나는 재검증 비용 없이 다음 수요에 다시 팔린다 — 한계비용이 0에 수렴하는 자산. 이 재사용률(persona reuse rate)이 단위경제(§7)의 핵심 레버이고, 측정·추적해야 할 1급 지표다.

| 단계 | 표현 방식 | 관찰(실행) 모델 | 입력 데이터 | 좋아지는 점 | 검증 깊이 |
|---|---|---|---|---|---|
| **Stage 1** (현재·PMF) | 베이스 LLM + 다이나믹 프롬프트 | **캡처-후-반응**: 사이트를 캡처(멀티스크린·인증·모바일·캡처플래너)하고 페르소나가 주 스크린샷+구조요약에 반응 | 유저 행동·세션 데이터 | PMF 증명 (코호트별 페르소나 ↔ 실제 행동 상관) | 데이터 무결성 (Walrus) |
| **Stage 2** | 페르소나 **온톨로지** (지식 그래프) | **자율 순회 (Mode C)**: 페르소나가 다음 액션을 고르며 화면을 옮겨다님 (browser-use). think-aloud 검증 게이트 통과가 착수 조건 | 자율 순회 행동·funnel 데이터 + 누적 테스트·설문 | 정형화 → 교차 쿼리·조합·상호운용 + 행동 funnel 측정 | 구조·출처 검증 (ontology + provenance) |
| **Stage 3** | **동결 base + 페르소나별 LoRA 어댑터** (멀티어댑터) | (Stage 2 실행 모델 유지) | 누적 페르소나-도메인 데이터셋 | 프롬프트 의존 ↓, 충실도 ↑, 추론비 ↓ | 학습 기여 검증 (어댑터 사용량 = 로열티 근거) |

> **실행 모델 주의 (원칙 5):** Stage 1의 "관찰"은 페르소나의 *자율 브라우징이 아니다*. 시스템이 사이트를 멀티스크린으로 캡처하고(로그인 게이트는 저장된 세션으로 통과, 모바일/단계 판별은 캡처플래너가 라벨링), 페르소나는 **주 스크린샷 1장 + 전 화면의 측정된 구조/단계 요약 텍스트**에 반응한다(비용상 N×이미지가 아님). 자율 순회는 **Stage 2 (Mode C)** 이며, 인간 think-aloud 데이터 게이트 통과 전까지 출시하지 않는다.

- 데이터 기층(Sui + Walrus)이 세 단계의 연료. 따라서 **데이터 소유·검증은 단순 기능이 아니라 로드맵 전체를 가능하게 하는 전제**다.
- Stage 3 제품 표면 = **동결 base(표준 모델) + 페르소나별 LoRA 어댑터를 멀티어댑터로 서빙하는 우리 LLM API**. base는 안 건드리고 페르소나마다 어댑터만 학습·교체 → base가 §3.1의 "표준"을 보장하고 어댑터가 페르소나별 *델타*. **1 base + N 어댑터** 구조(원칙 8). ⚠️ 멀티테넌트 프로덕션 서빙은 미해결 영역(§9·§11).
- **콜드스타트:** 페르소나 1인 데이터가 어댑터 학습에 충분치 않은 초기엔 **코호트 단위 어댑터**로 시작 → 데이터 누적 시 **개인 단위 어댑터**로 분화(2단계).

## 3. 시스템 아키텍처

### 3.1 설계 원칙: 3축 분리 (원칙 1)
| 축 | 어디서 나오나 | 위치 |
|---|---|---|
| 소유 (ownership) | 자산이 커밋되는 곳 (유저 키 소유 Sui object + Walrus blob) | 유저 사이드 |
| 실행 (execution) | 에이전트 오케스트레이션 | 유저 사이드 |
| 표준·검증 (standard/verify) | 모든 추론이 통과하는 LLM API | 플랫폼 사이드 |

**핵심**: 표준화는 "우리가 에이전트를 돌린다"가 아니라 **"우리 API가 곧 표준 모델"**에서 나온다. 에이전트는 유저 쪽(소유), 모델은 우리 쪽(표준). 양쪽의 장점만 취한다. 세 축이 인센티브가 어긋난 세 주체에 매핑되므로 어느 한쪽도 단독으로 결과를 위조할 수 없다.

> **실행 위치의 정밀화 (소유 ≠ 실행 기질):** "실행 = 유저 사이드"는 *실행의 통제·소유*(어떤 액션을 할지 페르소나가 결정, 키로 서명)를 뜻하지, 브라우저 렌더링·캡처·비밀자산 복호화가 반드시 유저 기기에서 일어난다는 뜻이 아니다. 신뢰가 필요한 두 경우 — ① 비밀 자산(§4.5 SealedAsset)을 유저 평문에 노출하면 안 될 때, ② 가짜 DOM farming(§6.2)을 막아야 할 때 — *실행 기질(substrate)*은 **플랫폼이 제공·attest하는 샌드박스**로 옮긴다. 통제·소유는 유저, 기질은 플랫폼. 이 분리가 §3.4의 3-tier 샌드박스 모델이다.

### 3.2 사이드별 책임

| 사이드 | 담당 | 상세 |
|---|---|---|
| **유저** | 에이전트 소유·실행 | 브라우저 자동화, 페르소나 소유·통제, 세션 트리거 |
| **우리 플랫폼** | 표준 API·시장·검증 앵커 | 표준 LLM API(추론 제공), 토큰 미터링·과금·정산, 검증 앵커(API 로그 + 샌드박스 캡처 서명) |
| **기업/의뢰자** | 수요·검증·소비 | 테스트 의뢰 + escrow 예치, GA 세션 검증, 결과 열람(결제·Seal 게이팅) |
| **온체인 레이어** | 공유 진실 | 페르소나(Sui object), 증거·메모리(Walrus/MemWal), Seal 접근제어, Escrow 정산 |

### 3.4 샌드박스 실행 모델 (3-tier) (원칙 2·3)

비밀 자산 격리(§4.5)와 관찰 무결성(§6.2)은 **같은 장치 하나**로 푼다 — 플랫폼이 제공하는 **신뢰된 실행 기질**. 신뢰 수준에 따라 3단계로 올린다.

| Tier | 실행 기질 | 보장 | 단계 |
|---|---|---|---|
| **T0 — 로컬** | 유저 기기 에이전트 (샌드박스 없음) | 없음 — 운영자/평판 신뢰. 비밀자산 캠페인 불가 | MVP, 비밀 없는 공개사이트 스캔 |
| **T1 — 플랫폼 샌드박스** | 플랫폼 호스팅 원격 브라우저. 유저 에이전트는 액션만 결정(드라이브), 페이지 fetch·렌더·캡처는 샌드박스가 수행 | 가짜 DOM 주입 차단 + SealedAsset 평문 미노출 + 캡처 플랫폼 서명 | **상호봉인 캠페인 필수 전제** |
| **T2 — TEE 샌드박스 (Nautilus)** | T1 샌드박스를 TEE(Nautilus/AWS Nitro) 안에서 실행 → "이 코드·이 입력 → 이 캡처/출력" attestation | **운영자 신뢰까지 제거** (전체 신뢰 제거는 아님 — 잔여: AWS HW + Seal 위원회) | v2 (프로덕션 빌드 성숙도 리스크) |

**T1 동작 (핵심):**
```
유저 에이전트 ──(트리거 / Mode C 시 다음 액션)──▶ 플랫폼 샌드박스(원격 브라우저)
                                      │ 실제 target/SealedAsset을 내부에서 fetch·복호화·렌더
                                      │ 행동/캡처 수집 → 플랫폼 서명
        페르소나 반응·행동로그 ◀───────┘  (유저는 '결과'만 소유, 비밀 '바이트'는 못 가져감)
```

- **T1은 Mode C를 요구하지 않는다 (중요):** T1의 최소 기능은 *비밀 격리 + 신뢰된 캡처*다. Stage 1(캡처-후-반응)에서는 샌드박스가 SealedAsset을 렌더·캡처하고 페르소나가 **그 캡처에 반응**하면 충분. 따라서 상호봉인은 **Mode C(Stage 2 게이트)를 기다리지 않고 T1만으로 Stage 1+에서 동작**한다.
- **소유는 유지:** 페르소나가 무엇을 할지 결정하고 키로 서명하는 통제권은 유저. 바뀌는 건 *어디서 렌더·복호화되느냐*뿐.
- **Mode C와 결합 시 복사누출이 추가 소거:** 테스터가 LLM 에이전트라 *사람 눈이 비밀 자산을 안 본다*.
- **남는 누출 면:** 샌드박스 출력(페르소나가 본 화면 요약)에 비밀이 새어나갈 수 있음 → 출력 측 redaction/워터마킹 + stake 슬래싱으로 보완. 완전 봉인은 T2(TEE).

## 4. 데이터 모델

### 4.1 Persona (Sui object)
- `owner`: 유저 지갑 주소
- `memwal_refs`: Walrus blob ID 리스트 (행동 데이터, 누적 세션 증거)
- `ontology_ref`: (Stage 2) 온톨로지 노드 참조
- `adapter_ref`: (Stage 3) 이 페르소나의 **LoRA 어댑터** blob 참조 + 학습된 base 모델 버전. *동결 base + 이 어댑터 = 이 페르소나*. 어댑터 가중치 자체가 owner 소유 자산(Walrus 저장). ⚠️ **소유 귀속은 정책 결정:** 어댑터는 유저 데이터 + 플랫폼 base·컴퓨트의 파생물이므로 "유저 소유"는 기술적 필연이 아니라 *선택한 정책*이다. 본 설계는 기여자 인센티브(§7 로열티)를 위해 유저 귀속을 택하고 Walrus/Sui로 *집행*한다 — 학습 비용 분담·라이선스 조건은 별도 합의 사항(§11).
- `meta`: 버전, 생성/갱신 시각, 도메인 태그
- 통제권: 전송·라이선스·폐기 모두 owner 서명 필요. Walrus 불변성으로 **이미 커밋된 것은 위조·변조 불가**. 어댑터도 동일 — 라이선스 없이는 base에 로드 불가(Seal 게이팅).

### 4.2 MemWal (Walrus blob)
- 세션 증거: DOM 스냅샷, 스크린샷/리코딩, 네트워크 트레이스, 행동 로그, LLM 추론 트레이스
- content-addressed → 무결성·가용성 검증
- (Stage 2) 온톨로지 구조 데이터 / (Stage 3) 학습용 정제 데이터셋 + **학습된 LoRA 어댑터 가중치**

### 4.3 Campaign / Escrow (Sui object)
- `requester`, `target` (URL/태스크 스펙), `reward_pool`(escrow 잠금), `persona_criteria`, `status`
- 정산 조건: 검증 통과한 세션 완료 시 escrow → 페르소나 owner 지급

### 4.4 Seal 접근 정책
- 페르소나·리포트 단위 암호화. 구매자(기업) 결제 → 복호화 키 → blob 열람.
- 개별 세션 데이터는 유저 보유, 집계 리포트는 기업 라이선스 열람.
- ⚠️ **잔여 신뢰 (정직):** Seal 복호화 키는 다수 제공자로 구성된 **t-of-n threshold 위원회**가 생성한다. 따라서 "중개자 없음"이 아니라 "중앙 중개자 → 분산 위원회"이며, 위원회 정족수 담합은 잔여 신뢰 가정(§6.3·§8). 또한 Seal은 *복호화 권한*만 통제하지 *복사*는 통제 못 함(DRM 일반 한계, §4.5.3).

### 4.5 상호봉인 캠페인 (Mutual-Sealed Campaign)

**목적:** 회사의 미공개 자산(출시 전 빌드/기능)과 유저의 행동 증거를 **양방향으로 봉인**해, 중앙 NDA·중개자 없이 "비밀 제품을 비밀 데이터로 교환"한다. 회사는 유출 없이 출시 전 테스트를 받고, 유저는 독점 얼리액세스 + 보상을 얻는다. `campaign.mutual = true`일 때만 활성.

#### 4.5.1 객체·blob 구성

**A. SealedAsset (회사 → 유저 방향)** — Walrus blob + Sui 참조
- `asset_blob_ref`: Walrus blob ID (Seal 암호화된 미공개 빌드/자료)
- `asset_hash`: 평문 해시 (복호화 후 무결성 대조용)
- `seal_policy`: 복호화 자격 술어 — `persona ∈ campaign.matched AND persona.opted_in == true`
- `reveal_condition`: opt-in 온체인 commit 완료 (+ 선택: 페르소나 stake 예치 / NDA attest)
- `meta`: 버전, 만료 epoch, 실행 모드(`sandbox_only` 플래그)

**B. SealedEvidence (유저 → 회사 방향)** — 기존 MemWal(§4.2) 재사용
- `evidence_blob_ref`: Walrus blob ID (Seal 암호화된 세션 증거)
- `seal_policy`: 복호화 자격 술어 — `requester.paid_into_escrow == true AND verification.passed == true`
- `reveal_condition`: 3-앵커 검증(§6) 통과 + escrow 결제 확인
- 소유: 유저 Persona object의 `memwal_refs`에 append (소유는 끝까지 유저)

**C. Campaign object 확장**
- `mutual`: bool
- `sealed_asset_ref`: SealedAsset(A) 참조
- `exchange_state`: enum `{ created → asset_sealed → persona_opted_in → asset_revealed_to_persona → evidence_committed → evidence_revealed_to_company → settled }`
- `atomicity_guard`: 회사 자산 공개와 유저 증거 공개를 escrow에 묶는 상태 잠금 (한쪽 이탈 시 슬래싱 근거)

#### 4.5.2 교환 순서 (상태머신) (원칙 6)

```
1. 회사: asset Seal 봉인 + escrow 예치              → asset_sealed
2. 매칭 페르소나: opt-in 온체인 commit (+선택 stake) → persona_opted_in
3. Seal 정책 충족 → 페르소나만 asset 복호화·테스트   → asset_revealed_to_persona
4. 유저: 세션 증거 Seal 봉인 → Walrus 커밋           → evidence_committed
5. 3-앵커 검증 통과 → 회사 evidence 복호화 자격 획득  → evidence_revealed_to_company
6. escrow → 유저 보상 정산                          → settled
```

- 양쪽 Seal 정책은 **서로 반대 방향**: 회사 자산은 "자격 갖춘 페르소나만", 유저 증거는 "결제+검증 통과한 회사만". 같은 캠페인 안에 두 정책이 공존.

#### 4.5.3 리스크·한계 (정직성 명시)

- **복사 누출 (근본 한계) + 민감도 상한:** 페르소나가 복호화한 미공개 빌드를 캡처·재배포하면 **Seal은 못 막는다**(DRM 일반 한계). 완화책: ① `sandbox_only`(평문 미노출, 플랫폼 봉인 실행) ② 페르소나 stake 슬래싱 ③ TEE 봉인(v2). → **운용 경계:** T1 상호봉인은 *저~중 민감도* 자산(곧 공개될 베타, 마케팅 프리뷰 등)까지만 안전. **고민감(전략적 미공개 코어)은 T2(TEE) 전까지 올리지 않는다** — 활성 시점(T1)과 완전 안전 시점(T2)의 갭이 이 기능의 핵심 제약.
- **원자성:** 진정한 atomic swap이 아니라 **escrow 매개 상태머신 + 슬래싱**으로 비협조를 처벌. 한쪽 중간 이탈 시 escrow/stake로 상대 보전(완전 동시성 미보장). — 비대칭 시점 교환에 atomic이 불가능할 때의 올바른 대체물(원칙 6).
- **자격 판정 신뢰:** `campaign.matched` 산정이 조작되면 비자격 페르소나가 자산 열람 가능 — 매칭 로직은 플랫폼 검증 앵커(§6)에 묶어야 함. **이 매칭 앵커가 T2에서도 남는 잔여 신뢰 중 하나**(§6.3).

## 5. 핵심 플로우 (캠페인 라이프사이클)

### 5.1 일반 캠페인 (공개 사이트, T0/T1)

```
1. 캠페인 생성        기업이 target·보상 정의, escrow에 보상 잠금 (Sui)
2. 매칭/opt-in        조건에 맞는 페르소나 owner가 참여 (on-chain commit)
3. 세션 실행          유저 에이전트가 target을 실제 테스트
                      └ 추론은 우리 LLM API 호출 (표준 모델)
4. 증거 커밋          세션 증거 → Walrus(MemWal), 페르소나(Sui object) 갱신
5. 검증               T0: 3중(모델출력·세션 GA·증거 Walrus) / T1: +샌드박스 캡처 = 4-신호(§6)
6. 게이팅 열람        기업 결제 → Seal 복호화 → 결과·리포트 열람
7. 정산               escrow → 유저 보상 지급 (Sui)
8. 성장/재사용 ★      페르소나 갱신 → 다음 캠페인·에이전트에 재사용 (복리 엔진 — §2)
```
★ 8단계가 사업적 복리의 원천. 검증된 페르소나의 재사용률을 1급 지표로 추적.

### 5.2 상호봉인 캠페인 (T1 샌드박스 필수)

§4.5 + §3.4 T1 결합. 모든 실행이 플랫폼 샌드박스 안. 괄호는 `exchange_state`.

```
1. 캠페인 생성(mutual)   회사가 SealedAsset Seal 봉인 + escrow 예치 (Sui)
                         정책 = "matched ∧ opted_in 페르소나만"          → asset_sealed
2. 매칭/opt-in          자격 페르소나 owner opt-in 커밋 (+선택 stake)      → persona_opted_in
3. 샌드박스 기동·자산공개  플랫폼 T1 샌드박스가 SealedAsset을 '내부에서' 복호화
                         + target 렌더. Seal 정책 충족 검증
                         (유저 평문엔 비밀 바이트 미노출)                 → asset_revealed_to_persona
4. 세션 실행            샌드박스가 렌더·캡처 → 페르소나가 캡처에 반응(Stage 1)
                         또는 액션 드라이브(Mode C, Stage 2 시)
                         └ 추론은 우리 LLM API / 캡처 플랫폼 서명
5. 증거 봉인·커밋        세션 증거 Seal 봉인(정책="결제 회사만") → Walrus  → evidence_committed
6. 4-신호 검증           모델출력·실행진위(샌드박스 서명 캡처)·증거(Walrus)·세션(GA)  (§6.4)
7. 게이팅 열람          회사 결제 확인 → Seal 복호화 자격                 → evidence_revealed_to_company
8. 정산·집행            escrow → 유저 보상. 비협조/누출 시 stake 슬래싱     → settled
```

**5.1과의 차이:** 양방향 봉인(반대 방향 Seal 정책 2개) · 샌드박스 강제(T1 필수, Mode C 불요) · 실행 진위 앵커 추가(4-신호) · atomicity_guard.

## 6. 검증 모델 (3-앵커 → T1+ 4-신호)

검증이 **한 곳에 몰리지 않고 여러 주체에 분산**된다(원칙 1·4). 어느 한쪽 단독으로 결과를 조작할 수 없다.

| 앵커 | 보증 대상 | 메커니즘 | 담당 |
|---|---|---|---|
| 모델출력 진짜성 | "이 입력에 모델이 이 출력을 냈다" | LLM API 호출 로그 (유저가 응답 위조 불가) | 플랫폼 |
| 세션 진짜성 | "진짜 이 세션이 사이트에 들어왔다" | GA instrumentation 교차확인 | 기업 |
| 증거 무결성 | "증거가 그대로다" | Walrus content-addressing | 온체인 |
| 실행 진위 (T1+) | "에이전트가 진짜 그 페이지를 봤다" | 샌드박스 서명 캡처 (§6.4) | 플랫폼 |

> **이미 깔린 다리:** 세션 진짜성 앵커는 신규 구축이 아니다. 현행 41rpm에 파트너 GA 비콘 인프라(`t.js` → `partner_behavior_events`, 워크스페이스 키 소스 라우팅)가 이미 라이브이며, 이것이 §6 세션 앵커의 작동하는 PoC다.

### 6.1 운영자 신뢰 제거 업그레이드 (v2 = §3.4 T2)
- **Nautilus(TEE) 1차 대상 = 샌드박스/검증 로직:** T2는 **§3.4의 T1 샌드박스(캡처·검증 실행 기질)를 TEE 안에 봉인**하는 것이 1차 — "이 코드·이 입력 → 이 캡처/검증결과" attestation으로 *운영자* 신뢰를 제거.
- ⚠️ **대형 LLM 추론 자체의 TEE 실행은 별개·고난도:** GPU-TEE(예: NVIDIA confidential computing)에 의존하며 Nautilus(AWS Nitro = CPU enclave) 범위 밖. 추론 진짜성은 당분간 §6 모델출력 앵커(API 로그)로 충당, 추론 TEE는 GPU-TEE 성숙 시 별도 트랙. v2에 묶지 않는다.
- ⚠️ **Nautilus 빌드 성숙도:** 프레임워크는 메인넷(2025-06-05)이나 공식 *참조 빌드 템플릿*이 보안 감사 미완료·평가 목적용. T2는 "도입 시점"만이 아니라 "프로덕션 빌드 성숙" 자체가 선행 조건(§11).

### 6.2 잔여 약점: 브라우저 관찰 무결성
- 유저 사이드 실행의 빈틈: 악의적 유저가 에이전트에 **가짜 DOM/화면**을 먹여 보상 farming 가능.
- ⚠️ **TEE로도 단독으로는 안 닫힌다:** TEE는 "이 입력→이 출력"만 증명하지 *입력이 진짜 현실인지*는 증명 못 함. fake DOM을 TEE에 넣으면 "이 fake DOM으로 이 출력"이 증명될 뿐. 따라서 **신뢰된 캡처 경로(샌드박스)가 TEE의 전제**다(원칙 4 — 의존 순서 명시).
- **완화책 (우선순위):** ① **플랫폼 샌드박스 캡처(§3.4 T1)** — 주된 해법 ② 기업 GA 교차검증 ③ TEE 봉인(§3.4 T2).

### 6.3 검증 수준 — tier별 (T0 → T1 → T2)
| | 소유 | 무결성 | 모델출력 진짜성 | 세션 진짜성 | 실행 진위 |
|---|---|---|---|---|---|
| MVP (Stage1, T0 로컬) | ✓ | ✓ Walrus | ✓ API 로그 | ✓ GA | ⚠️ 운영자 신뢰 (평판) |
| Stage1+ (T1 샌드박스) | ✓ | ✓ | ✓ | ✓ + 샌드박스 캡처 | ✓ 플랫폼 서명 캡처 (운영자 신뢰 잔존) |
| v2 (T2 TEE) | ✓ | ✓ | ✓ | ✓ | ✓ 운영자 신뢰 제거 |

> **"trustless"가 아니라 "trust-minimized" (정직):** T2조차 *모든* 신뢰를 제거하지 않는다. **잔여 신뢰 = { AWS Nitro 하드웨어/펌웨어 (attestation을 Amazon이 서명), Seal threshold 키서버 위원회 정족수, `campaign.matched` 매칭 앵커 }.** T2가 제거하는 것은 *운영자(우리)* 신뢰다. 피칭·문서에서 "trustless" 단어를 쓸 때 이 잔여 집합을 함께 명시한다.

### 6.4 샌드박스 = 신뢰된 캡처 경로 + 비밀 자산 격리 (원칙 3)
§3.4의 샌드박스는 검증 모델에서 **두 역할을 동시에** 한다 — 한 장치가 §6.2 갭과 §4.5 복사누출을 같이 막는다.
- **신뢰된 캡처 경로(§6.2 해소):** 페이지 fetch·렌더·캡처가 샌드박스 안에서 일어나고 산출물을 플랫폼이 서명 → "에이전트가 진짜 그 페이지를 봤다"가 모델출력 앵커와 별개의 실행-진위 앵커.
- **비밀 자산 격리(§4.5 해소):** SealedAsset 복호화가 샌드박스 내부에서만 → 유저 평문 미노출.
- **한계 (정직성):** T1은 *플랫폼(운영자) 신뢰* 잔존(→ T2). 샌드박스 *출력* 누출은 redaction/워터마킹 + 슬래싱으로만 완화.

## 7. 비용·인센티브 모델

- **양면 시장**: 수요측(기업)이 비용 부담, 공급측(유저)이 보상 수령. 유저에게 비용 전가가 아님.
- **우리 = 추론 제공자 + 마켓플레이스** (추론 마진 + 플랫폼 수수료).
- **정산 흐름**: 기업 escrow 예치 → 유저 에이전트 실행·API 호출 → 토큰 미터링 → escrow에서 (**추론비 + 샌드박스 실행비(T1/T2) + 유저 보상**) 정산. 샌드박스 호스팅(원격 브라우저·TEE)은 추론 외 인프라 원가이므로 단가에 별도 반영.
- **stake / 슬래싱 (상호봉인)**: §4.5에서 페르소나는 비밀 자산 열람 전 stake 예치, 누출·비협조 시 슬래싱되어 escrow 환수. 정직 행동의 본드.
- **로열티 (Stage 3)**: 페르소나별 LoRA 어댑터가 추론에 로드될 때마다(쿼리 단위) 어댑터 owner에게 사용량 기반 지속 보상. `adapter_ref` provenance + 멀티어댑터 서빙 로그가 정산 근거. ⚠️ 멀티테넌트 프로덕션 서빙 인프라에 의존(§9·§11).

> **단위경제는 순환 의존이다 (핵심 리스크):** 충실도(§8)가 입증돼야 기업 지불의사가 생기고 → 지불의사가 있어야 T1/T2 인프라 원가를 정당화하고 → 인프라가 있어야 충실도를 입증할 데이터를 모은다. 이 순환을 깨는 진입점은 **"충실도 PoC를 최소 인프라(T0)에서 먼저 돌려, 코호트 내 신호가 의사결정급인지 확인"**이다(§11). 특히 T2 TEE 원가가 *시뮬레이션* 단가를 *실사용자 테스트*보다 비싸게 만들면 시장이 성립하지 않는다 — §7 전체가 이 전제 위에 선다.

## 8. 탈중앙화 타당성 분석 (load-bearing test)

| 구성요소 | 판정 | 근거 |
|---|---|---|
| 페르소나 = 유저 소유 (Sui object) | **핵심** | 탈중앙이 더하는 건 *검열저항 소유*(운영자가 못 뺏음). 중앙 DB+포터빌리티로 "이식"은 되나 "운영자도 못 뺏음"은 안 됨 |
| 페르소나 LoRA 어댑터 = 유저 소유 (Stage 3) | **핵심 (정책 선택)** | 어댑터는 *유저 데이터 + 플랫폼 base·컴퓨트*의 파생물이라 소유 귀속은 기술 필연이 아니라 **선택한 정책**(§4.1). 온체인은 그 정책의 *집행 수단* |
| 증거 데이터 (Walrus) | **핵심** | 변조 불가 검증이 **무결성의 앵커**(신뢰 전체의 앵커가 아님 — 충실도는 별도 측정). 무결성 없이는 나머지가 무의미 |
| Seal 접근제어 | **핵심 (trust-minimized)** | 중앙 중개자 없이 유료·게이팅 가능. 단 t-of-n 키서버 위원회 신뢰 잔존(§4.4) |
| Escrow 정산 (Sui) | 조건부 | 오픈 마켓엔 필수, 내부 유저뿐이면 과함 |
| 추론 비용 탈중앙화 | 조건부 | 인센티브 설계(양면시장) 있어야 의미 |
| 인간 행동 진위 | 갭(완화 진행) | Walrus는 무결성만. 진위는 **샌드박스(T1, 1순위)+GA(독립신호)+TEE(T2)**로 단계 보완 |
| 측정 비교가능성 | 해소됨 | 표준 API로 실행 표준화 → 코호트별 상관 유지(아래 주) |

> **충실도 주의 (정직성 계약 — 문헌 정합):** 페르소나↔인간 일치도는 **단일 aggregate Pearson ρ로 제시하지 않는다.** 학술 문헌과 정합:
> - 여러 subjective 데이터셋에서 **데모그래픽 페르소나 변수는 인간 응답 분산을 대체로 한 자릿수%대(보고에 따라 ~10% 미만)만 설명** → 데모그래픽만으론 충실도가 약함(정확한 수치는 데이터셋·태스크 의존이며 인용 시 출처 명시 필요). **RPM의 차별점이 데모그래픽이 아니라 실제 행동 코퍼스 + 페르소나별 파인튜닝인 것이 바로 문헌이 가리키는 정답 방향**("더 풍부한 행동 데이터가 충실도를 올린다").
> - LLM 합성 응답은 **긍정 평가를 체계적으로 과대추정하고 분산이 실제보다 작음**(개인 차별화 부족). aggregate ρ는 코호트 혼합 시 약하거나 음수.
> - 문헌 합의: LLM 시뮬은 **절대 효과크기 추정이 아니라 상대 순위**(어느 변형이 이기나)에 쓰고, 그 순위조차 보이는 것보다 거칠다. **합성 페르소나는 실 응답자의 대체가 아니라 보완.**
> - 따라서 PMF 증거는 **코호트별 수치 + "어느 변형이 이기나"의 상대 순위 정확도**로 surface 한다.

**결론**: 상단 3개(소유·증거·게이팅)가 척추. Walrus가 load-bearing. 갭(진위)은 GA 교차검증으로 MVP 방어, 샌드박스(T1)→TEE(T2)로 단계 보완. **단, 시스템 전체는 충실도(§11)와 단위경제(§7·§11)라는 두 외부 가설 위에 선다.**

## 12. 보안·프라이버시 고려

- **개인정보**: 실제 인간 행동 데이터는 민감정보. Seal 암호화 + 수집 동의 + 익명화/가명화 필수.
- **키 관리**: 유저 지갑이 소유권 루트. 분실·위임 정책, 소셜 리커버리 검토.
- **API 인증·쿼터**: 유저 에이전트 LLM API 호출 인증, 캠페인 단위 쿼터·레이트리밋.
- **데이터 폐기 (crypto-shredding 1차):** Walrus deletable blob + 스토리지 epoch 만료로 "잊혀질 권리". ⚠️ 단 복호화 키가 이미 유출됐다면 불변 blob은 영구 노출 가능 — 실질 삭제 보장은 **키 폐기(crypto-shredding)**다. Seal 키 폐기를 1차 메커니즘으로, blob 만료를 2차로.
- **샌드박스 보안 (T1/T2)**: ① T1은 *운영자 신뢰* 잔존(→ T2). ② 출력 누출 → redaction/워터마킹 + 슬래싱. ③ 샌드박스가 임의 URL/비밀자산을 fetch·렌더하므로 **SSRF·악성 콘텐츠 격리**(네트워크 이그레스 제한, 1회용 컨테이너) 필수.
- **잔여 신뢰의 공격면 (신규):** Seal 키서버 위원회 정족수 공모, AWS Nitro 펌웨어 신뢰, 매칭 앵커 조작 — 각각을 위협 모델에 명시하고 모니터링·다양화(키서버 제공자 분산)로 완화.

## 부록 A. 용어
- **MemWal**: Walrus에 저장되고 Sui object로 소유되는 검증 가능한 페르소나 메모리 객체.
- **3-앵커 / 4-신호 검증**: 모델출력(플랫폼)·세션(기업 GA)·증거(Walrus)에 T1+에선 실행진위(샌드박스 서명 캡처) 추가.
- **2-channel analysis**: 행동 채널과 응답 채널을 분리 수집·분석.
- **페르소나 LoRA 어댑터**: Stage 3에서 페르소나별 행동 데이터로 학습한 LoRA 가중치. 동결 base + 이 어댑터 = 그 페르소나. owner 소유(Walrus 저장, Seal 게이팅), 쿼리당 로열티 단위.
- **멀티어댑터 서빙**: 하나의 동결 base에 다수 LoRA 어댑터를 요청별로 끼워 추론(vLLM multi-LoRA / S-LoRA).
- **샌드박스 tier (T0/T1/T2)**: 실행 기질 신뢰 단계 — T0 유저로컬 / T1 플랫폼 샌드박스 / T2 TEE.
- **trust-minimized**: trustless의 정직한 대체어. 운영자 신뢰는 제거하되 잔여 신뢰(AWS HW, Seal 위원회, 매칭 앵커)는 명시.
- **재사용률 (persona reuse rate)**: 검증된 페르소나 1개가 재검증 없이 N개 캠페인에 재판매되는 비율 — 단위경제의 복리 레버.

## 부록 B. 개정 이력 (요약)
- **v0.1**: 초기 설계. 체인 전환을 암묵 가정.
